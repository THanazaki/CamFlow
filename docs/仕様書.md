# CamFlow 仕様書

個人カメラマン向け撮影管理 PWA。本書は **実装済みコードの仕様**をまとめたもの。

- 対象コミット: `98b0533` 以降（2026-11-03 時点）
- 実装規模: TypeScript / SQL 約 4,500 行
- **現状の到達点**: DB スキーマと同期基盤（土台）まで。Phase 1 の業務画面は未実装

---

## 1. 概要

### 1.1 目的

個人カメラマンの撮影ライフ（予約・スケジュール・現場タイマー・モデルマスター・データ管理）を最適化する。

### 1.2 Phase 1 の機能範囲

| 機能 | 状態 |
|---|---|
| 撮影スケジュール・枠管理 | DB のみ（画面未実装） |
| モデルマスター管理 | 一覧画面のみ（暫定。登録・編集は未実装） |
| 現場用撮影タイマー | DB・同期のみ（画面未実装） |
| データ・納品ステータス管理 | DB・ビューのみ（画面未実装） |

### 1.3 前提条件（確定事項）

1. **金銭はカメラマン側の「支出」のみ**を扱う。請求・入金管理は対象外
2. **1つの撮影枠に複数モデルが入りうる**（ペア撮影・コラボ）
3. **写真の実データは保存しない。** 保管先パス・枚数・容量などのメタ情報のみ記録
4. **カメラマン専用の最小構成。** 運営・モデル側ログインは将来の拡張
5. **メール＋パスワードのアカウント制。** ログイン画面を reCAPTCHA で保護する
6. **完全オフライン同期**を自前実装（IndexedDB + outbox + Last-Write-Wins）

### 1.4 技術スタック

| 領域 | 採用 | バージョン |
|---|---|---|
| フレームワーク | Next.js (App Router) | 16.4.4 |
| UI | React / Tailwind CSS | 19.3.0 / v4 |
| バックエンド | Supabase (Auth / PostgreSQL / Storage) | PostgreSQL 17 |
| ローカルDB | Dexie (IndexedDB) | 4.x |
| Service Worker | Serwist | 9.x |
| テスト | Vitest / fake-indexeddb / PGlite | 4.x / 6.x / 0.3.x |

## 2. システム構成

### 2.1 データフロー

```
┌─────────────────────────────────────────────┐
│  画面（全て Client Component）                │
│    読み取り: useLiveQuery(db.models...)      │
│    書き込み: createRow / updateRow / ...     │
└───────────────┬─────────────────────────────┘
                │
       ┌────────▼─────────┐
       │ Dexie (IndexedDB)│  ← アプリにとっての唯一のデータソース
       │  9テーブル        │
       │  _outbox / _meta │
       └────────┬─────────┘
                │ lib/sync（push → pull）
       ┌────────▼─────────┐
       │  Supabase        │
       │  PostgreSQL + RLS│
       └──────────────────┘
```

### 2.2 設計上の帰結

**ローカルファースト = 実質クライアント SPA。**
全ての読み取りが IndexedDB 由来になるため、Server Components でデータを描画できない。
Next.js はルーティングとビルドのために使い、データを持つ画面は全て Client Component とする。
Server Actions もデータ取得には使わない。

静的エクスポート（`output: 'export'`）は**採用しない**。`/models/[id]` のような動的ルートは
ID がサーバー側で分からず `generateStaticParams` を書けないため。
オフラインの cold start は Service Worker の navigation fallback で担保する。

## 3. データベース仕様

### 3.1 ER 構成

```
auth.users ─1:1─ profiles
           ├─1:N─ models        モデルマスタ
           │        └─1:N─ model_former_names   旧名義
           ├─1:N─ venues        スタジオ / ロケ地マスタ（kind で区別）
           ├─1:N─ organizers    団体マスタ（撮影会の主催団体）
           └─1:N─ sessions      撮影イベント（1日 / 1案件）
                    │  ├ venue_id     → venues
                    │  └ organizer_id → organizers
                    └─1:N─ slots         撮影枠（1部・2部…）＝ タイマーの単位
                             └─1:N─ slot_models   枠 × モデル ＝ 支払い・納品の単位
                                      └ model_id → models

shoot_history ─1:N─ shoot_history_models   遡及登録した過去の撮影
  ├ venue_id     → venues
  ├ organizer_id → organizers
  └ model_id     → models

sync_tombstones                  物理削除ログ（オフライン同期用）
audit_logs                       DB 操作ログ（端末には同期しない）
```

**データは「運用フロー」と「遡及登録」の2系統に分かれる。**

| 系統 | テーブル | 入口 |
|---|---|---|
| 運用フロー | `sessions` / `slots` / `slot_models` | 予約情報入力 → 確定撮影情報入力 → 撮影情報 |
| 遡及登録 | `shoot_history` / `shoot_history_models` | 過去撮影登録 |

分けた代償として「過去の撮影」が2か所に存在する。片方しか見ないと必ず数が合わなくなるため、
**統計・検索の画面は個別テーブルではなく `v_shoot_history_all` / `v_model_stats` を見ること。**

**マスタは4種**: モデル（`models`）/ スタジオ（`venues.kind = 'studio'`）/
ロケ地（`venues.kind = 'location'`）/ 団体（`organizers`）。

スタジオとロケ地は一覧を分けたいだけで持つ項目が共通のため、テーブルは `venues` 1つにして
種別カラムで分ける。テーブルを割ると `sessions.venue_id` の参照先が2つになり、
結合も RLS も二重になる。

**単位の考え方**

| テーブル | 1行が表すもの | 主な用途 |
|---|---|---|
| `sessions` | 撮影イベント1件（例: 11/3 スタジオ○○ 個人撮影会） | カレンダー表示、セッション単位の経費 |
| `slots` | その中の撮影枠（1部・2部…） | **現場タイマー**、撮影データの保管先 |
| `slot_models` | 枠に参加したモデル1人分 | **モデル料の支払い**、**納品** |

1枠に複数モデルが入りうるため、支払いと納品は枠ではなく `slot_models` が単位になる。

### 3.2 ENUM 型

| 型名 | 値 | 用途 |
|---|---|---|
| `model_status` | `active` / `inactive` / `ng` | 活動中 / 休止・引退 / （`ng` は使わない。画面では休止・引退として扱う） |
| `venue_kind` | `studio` / `location` | スタジオ / ロケ地 |
| `booking_method` | `page` / `email` / `dm` | 予約ページ / メール / DM |
| `shoot_type` | `solo` / `event` / `client` / `personal` | 個人撮影会 / 撮影会イベント / 依頼撮影 / 自主制作 |
| `shoot_category` | `solo` / `group` / `session` / `large` | 個撮 / 団体 / セッション / 大撮 |
| `place_category` | `outdoor` / `studio` | 屋外 / スタジオ |
| `fee_payment_timing` | `on_the_day` / `in_advance` / `paid` | 撮影料の支払方法。当日 / 事前 / 支払済み |
| `session_status` | `planned` / `confirmed` / `done` / `cancelled` | イベントの進行状態 |
| `timer_status` | `idle` / `running` / `paused` / `finished` | 現場タイマーの状態 |
| `shoot_status` | `planned` / `shot` / `cancelled` / `no_show` | 枠の実施結果 |

**所有者検証トリガが必要な理由**: `user_id` を冗長保持しているため、RLS だけでは
「自分の `user_id` を入れつつ他人の `session_id` を参照する」書き込みを防げない。
外部キーは所有者を検証しないため、トリガで担保する。

### 3.7 RLS

全テーブルで有効。ポリシーは「所有者のみ全操作可」の1本に統一する。

```sql
create policy <table>_owner_all on public.<table>
  for all to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);
```

- `profiles` は `id` で判定
- `sync_tombstones` は `select` のみ（書き込みはトリガが行う）
- `audit_logs` も `select` のみ。本人でも書き換えや削除はできない
- 未ログイン（`anon`）はポリシーが存在しないため 0 行・書き込み不可
- `auth.uid()` を `(select auth.uid())` で包むのは Supabase 推奨の最適化。
  行ごとの再評価ではなく InitPlan として1回だけ評価される

### 4.2 `_dirty` フラグ

ローカル行は サーバー行 + `_dirty: 0 | 1` を持つ。

- `1` = この行に未送信の変更がある
- **pull はこの行を上書きしない**（未送信のローカル変更を消さないため）
- outbox が空になった時点で `refreshDirtyFlag()` が `0` に戻す

|---|---|
| `seq` | 自動採番。**これが送信順** |
| `table` | 対象テーブル |
| `op` | `insert` / `update` / `delete` |
| `row_id` | 対象行の id |
| `row_key` | `${table}:${row_id}`。圧縮のグループキー |

| `status` | `pending` / `failed` |
| `attempts` | 試行回数 |
| `last_error` | 直近のエラーメッセージ |
| `created_at` | |

## 5. 同期仕様

### 5.1 全体フロー

`sync()` は **push → pull** の順に実行する。

push を先にする理由: 未送信のローカル変更がある行を pull が上書きしないため。
先に押し出してから取り込めば、サーバーの正規版（`updated_at` がサーバー時刻で付き直ったもの）が
そのまま入ってくる。

### 5.2 起動契機

| 契機 | 実装 |
|---|---|
| アプリ起動 | `useSyncEngine()` → `startSync()` |
| オンライン復帰 | `window` の `online` イベント |
| タブ復帰 | `document` の `visibilitychange` |
| 定期ポーリング | 60秒間隔 |
| 再試行 | 指数バックオフ: 1s → 5s → 15s → 60s → 300s |
| 手動 | 同期インジケータの「同期」ボタン |

実行中に `sync()` が呼ばれた場合は多重実行せず、「もう1回やる」だけ記録して終了後に再実行する。

### 5.3 書き込み（mutations）

**ローカル行の変更と outbox への追加を同一 Dexie トランザクションで行う。**
分けると、片方だけ成功したときに次の破綻が起きる:

- ローカルだけ変わって永遠に送信されない変更
- 送信キューにあるのに手元には無い変更

| API | 動作 |
|---|---|
| `createRow(table, values)` | `id` / `created_at` / `updated_at` をローカルで採番。`_dirty = 1`。戻り値は id |
| `updateRow(table, id, patch)` | **差分だけ**を outbox に積む（行全体を送らない） |
| `deleteRow(table, id)` | 物理削除（主に `slot_models` 用） |
| `softDeleteRow(table, id)` | `deleted_at` を立てる。論理削除があるテーブルはこちらを使う |

`id` はサーバーの採番を待たずクライアントで生成する（オフラインでも即座に画面に出すため）。

### 5.4 outbox の圧縮（compact）

オフライン中に同じ行を何度も編集すると update が積み上がる。送信前に畳む。

| パターン | 結果 |
|---|---|
| `insert` → `update`* | `insert` 1件（payload をマージ） |
| `insert` → `delete` | **両方破棄**（サーバーは存在を知らない） |
| `update` → `update`* | `update` 1件（後勝ちでマージ） |
| `update` → `delete` | `delete` 1件（直前までの update は破棄） |
| `delete` → `update` | `update` を破棄 |
| `delete` → `insert` | 畳まず順番を保つ（同じ id の作り直し） |

出力は各 op の最小 `seq` 順。**テーブルをまたいだ相対順序（FK の親→子）が保たれる。**
各 op は元エントリの `seq` を `sourceSeqs` に持ち、送信成功時にまとめて削除する。

### 5.5 push

- **`seq` 昇順の直列送信。** 並列化すると FK の親より子が先に届きうる
- `insert` は **upsert** で送る。再送しても重複キーで落ちない
- **恒久的エラーは outbox に `failed` として残し、UI に出す。黙って捨てない**。後続の op は継続
- **再試行可能なエラーはそこで打ち切る。** 飛ばして先に進むと順序が崩れる

戻り値 `PushResult`: `pushed` / `failed` / `discarded` / `interrupted`

### 5.6 エラー分類

誤って「再試行可能」に分類すると、壊れた書き込みを永遠に再送し続けてキューが詰まる。

| 判定 | 条件 |
|---|---|
| **恒久的** | HTTP 4xx（408 / 429 を除く）、SQLSTATE `22`/`23`/`42` 始まり、`PGRST` 始まり |
| **再試行可能** | HTTP 408 / 429 / 5xx、`fetch` 失敗（オフライン） |

### 5.7 pull

テーブルごとに `SYNC_TABLES` の順（FK の親から子へ）で差分取得する。

**ページング**: `(updated_at, id)` のキーセットページング、1ページ 500件。

```sql
-- 2ページ目以降（updated_at が同値の行をまたいで進む）
updated_at.gt.<cursor>, and(updated_at.eq.<cursor>, id.gt.<lastId>)
```

**2秒のオーバーラップ（`OVERLAP_MS = 2000`）** — 必須。
`updated_at` はトリガの `now()` ＝**トランザクション開始時刻**なので、
「後に開始したトランザクションが先にコミットする」と小さい `updated_at` の行が後から見える。
ウォーターマークをコミット順で進めると取りこぼす。upsert は冪等なので重複取得は無害。

**適用ルール**
- `_dirty = 1` の行は上書きしない（`skippedDirty` にカウント）
- `deleted_at` が入っている行はローカルから削除（論理削除の伝播）
- それ以外は `_dirty = 0` で upsert

**物理削除の取り込み**
`sync_tombstones` を `id > lastTombstoneId` で読み、該当行をローカルから削除する。
`_dirty = 1` の行は消さない（push の結果を待つ）。

**フル再同期フォールバック**
最後の同期が tombstone の保持期間（90日）より古い場合、その間の物理削除を知る手段が無い。
差分では整合が取れないため、ローカルテーブルを捨てて全件取り直す。

戻り値 `PullResult`: `upserted`（テーブル別）/ `removed` / `skippedDirty` / `fullResynced`

### 5.8 競合解決（Last-Write-Wins）

**サーバーの `updated_at` が常に権威。**
`set_updated_at()` トリガがサーバー側の書き込みで必ず上書きするため、クライアントの時計は信用しない。
衝突時は「後からサーバーに届いた書き込みが勝つ」。

### 5.9 同期状態（SyncState）

| フィールド | 内容 |
|---|---|
| `phase` | `idle` / `syncing` / `offline` / `error` |
| `lastSyncedAt` | 最終成功時刻 |
| `pending` | 未送信件数 |
| `failed` | 送信失敗件数 |
| `error` | エラーメッセージ |

`useSync()` が状態と操作（`syncNow` / `retry` / `discard`）を返す。

### 5.10 タイマーとオフライン

タイマーは `timer_ends_at`（絶対時刻）を保存する設計のため、オフライン中もローカルだけで正しく動く。

- 残り時間はクライアントで `timer_ends_at - now()` を計算する
- 一時停止中のみ `timer_remaining_sec` を使い、再開時に `timer_ends_at = now() + timer_remaining_sec` を書き直す
- これにより PWA のリロード・バックグラウンド復帰・別端末間で状態が一致する
- タイマー操作も通常の書き込みとして outbox を通る

### 6.2 reCAPTCHA

> **現在は一時的に外している**（`lib/auth/recaptcha.ts` の `RECAPTCHA_ENABLED = false`）。
> スクリプトを読み込まず、ログイン画面の表示も出さず、`/api/auth` の検証も本番を含めて省く。
> 戻すときは `true` にする。以下は有効にしたときの仕様。

**Supabase Auth の CAPTCHA 連携は hCaptcha と Cloudflare Turnstile のみで、
reCAPTCHA は選べない。** そのため自前で検証する。

```
ログイン画面 ──token──> /api/auth ──secret+token──> Google siteverify
                           │
                           └──> Supabase Auth（サーバ側で実行）
                                    │
                           session ─┘ ──> クライアントが setSession
```

- reCAPTCHA v3（透明・スコア方式）。しきい値は `RECAPTCHA_SCORE_THRESHOLD`（既定 0.5）
- スクリプトはログイン画面を開いた時点で読み込む（初期表示を重くしない）
- 秘密鍵が未設定のとき: 開発では検証をスキップして警告、**本番では拒否する**
- `/api/auth` は入力の検証 → CAPTCHA → Supabase の順。
  設定チェックを先に置くと利用者の入力エラーが 500 に埋もれるため

> **この reCAPTCHA の限界**: 守れるのは `/api/auth` 経由のフォームだけ。
> anon キーは公開前提なので、攻撃者は Supabase の認証エンドポイントを直接叩いて
> reCAPTCHA を飛ばせる。Supabase 側で強制したいなら hCaptcha か Turnstile に替える。

### 6.3 テストアカウント

`test` / `test` でサインインできる。**本番（デプロイ先）でも有効**（`lib/auth/test-account.ts`）。

- Supabase も reCAPTCHA も用意せずに画面を触れるようにするためのもの
- Supabase のユーザーではないので**同期はされず、データはその端末にだけ残る**
  （Supabase のセッションを発行しないので、サーバのデータは読めず、送ろうとしても RLS で弾かれる）
- 固定ID `00000000-0000-4000-8000-000000000001` を使う。
  サインインし直してもローカルのデータは残る
- **無効にするときは `NEXT_PUBLIC_DISABLE_TEST_ACCOUNT=true` を設定してビルドし直す。**
  API の分岐とログイン画面の案内の両方が消える。`NEXT_PUBLIC_` の値はビルド時に埋め込まれるため、
  デプロイ先で設定を変えただけでは反映されない
- 本番で有効なので、URL を知っている人は誰でも `test` / `test` でアプリに入れる。入れるのはその端末の中だけ
- メール欄は `type="text"`。ブラウザ側のメールアドレス形式チェックはかけず（`test` を打てるように）、
  形式の確認は Supabase Auth に任せる。スマホではメール用のキーボードを出す（`inputMode="email"`）

### 6.4 ローカルデータとアカウントの対応

**別のユーザーでサインインしたら IndexedDB を空にする。**
RLS が守るのはサーバだけで、ローカルの中身はその端末を使う誰でも読める。
消さないと前のユーザーの撮影履歴が次のユーザーに見えてしまう。

サインアウトでもローカルを消す（同じ端末を別の人が使う可能性があるため）。
確認ダイアログでその旨を伝える。

### 6.5 オフライン時

セッションを確認できない場合（オフライン、セッション切れ、Supabase 未設定）は、
`_meta['auth:userId']` に残した前回のIDで続行し、`offlineFallback` を立てる。
これが無いと「完全オフライン」と言いながら電波が無いと何も読み書きできない。

認証の迂回には使えない。サーバのデータは RLS で守られており、有効なトークンが
無ければ同期できない。ここで見えるのは、その端末にすでに入っている
（devtools で誰でも読める）ローカルデータだけ。

### 6.6 公開 API

`getAuthState()` / `subscribeAuth()` / `useAuth()` / `initAuth()` /
`applySession()` / `applyLocalSession()` / `signOut()` / `getActiveUserId()`

**RLS は有効なまま維持する。** 外すと本番に戻し忘れたとき全データが公開される。

## 7. PWA 仕様

### 7.1 Service Worker のビルド方式

**`next.config.ts` のプラグイン（`withSerwistInit`）は使わない。**
Next.js 16 は dev / build とも Turbopack が既定だが、`@serwist/next` のプラグインは
webpack プラグインとして動くため **Turbopack では警告だけ出してビルドが成功し、SW が生成されない**。

採用: **configurator モード** — `serwist.config.mjs` + `serwist build`。
`next build` の後段で SW を単体ビルドするのでバンドラに依存しない。

- 設定ファイルが `.mjs` なのは、`@serwist/cli` が素の `import()` で読むため（Node 20 は TS を直接読めない）
- SW の登録は `RegisterServiceWorker.tsx` が行う（プラグインの自動登録が無いため）
- 開発中（`npm run dev`）は SW を生成せず、登録も試みない

### 7.2 キャッシュ戦略

| 項目 | 内容 |
|---|---|
| precache | アプリシェル（JS / CSS / プリレンダリング済み HTML / アイコン）約23 URL |
| runtime | `defaultCache`（Next.js 向けの既定戦略） |
| navigation fallback | `/~offline` |
| その他 | `skipWaiting` / `clientsClaim` / `navigationPreload` 有効 |

**precache と navigation fallback の両方が必要。**
データは全て IndexedDB にあるので通信が無くても画面は作れるが、アプリシェル自体が
キャッシュから出せないとオフラインの cold start（オフラインのまま再起動）で白画面になる。

### 8.6 ダッシュボード

上段に3つのリマインド、下段に直近の撮影済みデータ。
クエリは `src/lib/queries/dashboard.ts` に集約する（理由は下記）。

**リマインドは工程の「区間」で定義する。** 日付が未来かどうかではない。
可否が決まらないまま日が過ぎた予約や、撮影したのにデータ未登録の枠こそ出すべきもの。

```
予約情報入力 ──[予約可否決定]── 撮影確定 ──[撮影]── 撮影データ登録 ── 完了
   └─ 予約リマインド ─┘        └──────── 撮影リマインド ────────┘
```

| カード | 条件 | 並び |
|---|---|---|
| 予約リマインド | `sessions.status = 'planned'`（可否未決定）の枠 | 期限超過を先頭に、以降は予定日の近い順 |
| 料金リマインド | 確定した撮影（`confirmed` / `done`）の撮影料（`slots.booking_fee`）。支払方法が当日なら撮影日の撮影開始時刻、事前なら支払日を期日にする。支払済み・未選択は出さない。撮影が終わったら出さない | 期日の近い順。事前で支払日が未入力のものが先頭 |
| 撮影リマインド | `sessions.status = 'confirmed'` かつ `slots.storage_path` も `storage_urls` も空の枠 | 同上 |

各行には工程バッジを出す。

| バッジ | 意味 |
|---|---|
| 可否待ち / 可否未決 | 予約の可否が未決定。後者は予定日を過ぎている |
| 撮影前 / データ未登録 | 確定済み。後者は撮影日を過ぎて保管先が未入力 |

- 中止・不参加（`shoot_status` が `cancelled` / `no_show`）の枠はどちらにも出さない
- カードのバッジは表示件数（最大5件）ではなく**該当総数**
- 撮影リマインドは `storage_path` か `storage_urls` が入った時点で消える。
  **データ登録が完了したら `sessions.status` を `'done'` にする想定**で、
  `'done'` の枠はリマインドの対象外になる
- 下段は撮影済みの枠と遡及登録を日付の降順で10件。保管先・バックアップが
  未登録の行は警告色で出す

> **なぜクエリ層が要るか**: サーバ側の `v_shoot_history_all` / `v_model_stats` は
> ビューなので Dexie に同期されず、画面からは引けない。ローカルファーストでは
> 「ビュー相当」をクライアントに用意する必要がある。画面が `db.slots` などを
> 直接組み立てると同じ結合ロジックが散らばって必ずズレるため、
> 読み取りは `src/lib/queries/` に集約する。

### 8.7 業務フローと画面の対応

通常フローは次の順に進む。

```
予約管理             撮影管理                    統計情報
 予約情報入力  ──→  確定撮影情報入力  ──撮影──→  撮影情報   ──→  予約可否情報
 （枠を押さえる）     （内容を確定）              （保管先を登録）   過去撮影情報
                                                                    撮影料積算
                      ▲
過去撮影データ管理     │ このフローに乗っていない過去の撮影だけを
 過去撮影登録  ───────┘ 後から取り込む
 撮影情報検索
```

**「撮影情報」と「過去撮影登録」は、レコードを更新するのか新規作成するのかが異なる。**

| | 撮影管理 > 撮影情報 | 過去撮影データ管理 > 過去撮影登録 |
|---|---|---|
| 対象 | 「確定撮影情報入力」で**作成済み**の撮影 | 「確定撮影情報入力」を**通していない**過去の撮影 |
| 操作 | 既存の `slots` を**確認・更新** | `shoot_history` / `shoot_history_models` を**新規作成** |
| 入力タイミング | 撮影後 | 任意（遡及） |
| 主な入力項目 | `storage_path` / `storage_label` / `storage_size_mb` / `frame_count` / `backup_location` / `backed_up_at`、`shoot_status` を `shot` へ | 撮影会名から撮影日まで、ストレージURL（→ 8.11） |

「撮影情報」はスケジュールの確認と、撮影後の保管先登録の両方を担う。

スキーマ上の注意:

- 遡及登録でもタイマーは動いていないため `timer_status = 'idle'`（タイマー系カラムは全て NULL）。
  `slots_timer_consistency` 制約と矛盾しない
- `slots.start_at` と `slot_no` は NOT NULL。遡及登録でも過去日時と枠番号の入力が必要
- 遡及登録でモデルを指定する場合、`models` に存在しなければ先に作る
  （`slot_models.model_id` は `models` への外部キー）

### 8.8 予約情報入力 / 予約スケジュール

**予約受付の開始日時（`sessions.booking_opens_at`）は撮影日とは別軸。**
個人撮影会では受付が始まる時刻が決まっていて、その時刻に枠を取りに行く。
予約スケジュールはこの時刻までのカウントダウンを出す。

入力項目（この順。`*` は必須）

| # | 項目 | 必須 | 保存先 | 補足 |
|---|---|---|---|---|
| 1 | 撮影会名 | | `sessions.title` | 未入力ならコンセプト → `{モデル名} 撮影`（モデルなしの区分は区分名）の順でタイトルを作る |
| 2 | 撮影区分 | `*` | `sessions.shoot_category` | 個撮 / 団体 / セッション / 大撮。既定は個撮 |
| 3 | モデル名 | `*` | `slot_models.model_id` | **セッション・大撮では欄を出さず、`slot_models` を作らない。** それ以外はマスタに無ければ `models` を新規作成する。`model_id` は NOT NULL でテキストのフォールバックが無いため |
| 4 | 撮影コンセプト | | `sessions.concept` | |
| 5 | 場所 | | `sessions.venue_id` / `venue_name` | マスタに同名があれば紐づけ、無ければテキストのみ。予約のたびに場所マスタが増えるのを避ける |
| 6 | 撮影日 | `*` | `sessions.session_date` | |
| 7 | 予約開始日時 | `*` | `sessions.booking_opens_at` | |
| 8 | 予約種類 | `*` | `sessions.booking_method` | 予約ページ / メール / DM。既定は予約ページ |
| 9 | 予約URL | `*` | `sessions.booking_contact` | **予約種類でラベルと入力型が変わる**（URL / メールアドレス / DM送付先） |

続けて、次の項目も入力できる。いずれも任意で、確定撮影情報入力と同じ欄・同じ保存先。

| 項目 | 保存先 | 補足 |
|---|---|---|
| 撮影料（円） | `slots.booking_fee` | 空欄は0円。0以上の整数 |
| 支払方法 | `slots.fee_payment_timing` | 当日 / 事前 / 予約時。撮影料の隣に出す。既定は未選択。**「予約時」は値としては `paid`** で、確定撮影情報入力には「支払済み」として引き継ぐ。予約スケジュールの表示も「予約時」 |
| 支払日 | `slots.fee_payment_date` | 事前のときだけ欄を出す |
| 衣装系オプション | `slots.costume_options` | |
| 撮影方法オプション | `slots.shooting_method_options` | |

最後にメモ（`sessions.memo`、任意）を入力できる。予約スケジュールのカードに表示し、確定撮影情報入力で予約を選ぶと引き継ぐ。

撮影会名・モデル名・場所は過去の入力を `datalist` で候補に出す。

1件の予約は `sessions` + `slots` + `slot_models` の3行になる。
`createRow` はテーブルごとに別トランザクションだが、outbox は seq 昇順に直列送信されるので
親 → 子の順に呼べば FK の順序は保たれる。

- `sessions.status` は `'planned'`（可否未決定）で作る
- 予約段階では枠の時刻が未定のため、`slots.start_at`（NOT NULL）には撮影日の 0 時を仮置きし、
  「確定撮影情報入力」で実時刻に直す想定
- スケジュール画面は `status = 'planned'` を `booking_opens_at` 昇順で表示。
  未設定は末尾。受付開始を過ぎたものは「受付中」として強調する
- スケジュール画面のカードには、撮影料・支払方法と支払日・各オプションを入力があるときだけ表示する（編集はできない）
- 「確定撮影情報入力」で予約を選ぶと、撮影料・支払方法・支払日・各オプションも引き継ぐ。
  確定時はフォームの値で枠を更新するので、引き継がないと予約時の入力が消える
- 申込先は予約種類に応じて見せ方を変える。`page` はリンク、`email` は `mailto:`、
  `dm` はテキスト表示（リンクにできないため）
- カウントダウンは `useSyncExternalStore` で1秒ごとに更新する。
  サーバ側スナップショットは 0（非表示）にして、ハイドレーション不整合を避ける

### 8.9 確定撮影情報入力

予約が取れた撮影の確定内容を登録する。**予約から確定する経路と、予約を通さず直接登録する経路の両方**を扱う。
どちらも最終的に `status = 'confirmed'` の session + slot + slot_models になる。

| # | 項目 | 必須 | 保存先 |
|---|---|---|---|
| — | 予約から選ぶ | | 選ぶと内容を引き継ぎ、その予約を確定にする。選ばなければ新規作成 |
| 1 | 撮影会名 | | `sessions.title` |
| 2 | 撮影区分 | `*` | `sessions.shoot_category`（予約から選ぶと引き継ぐ。NULL の予約は個撮） |
| 3 | モデル名 | `*` | `slot_models.model_id`（マスタに無ければ `models` を作成）。セッション・大撮では欄を出さない |
| 4 | 撮影コンセプト | | `sessions.concept` |
| 5 | 場所区分 | `*` | `sessions.place_category`（屋外 / スタジオ。既定はスタジオ） |
| 6 | 場所 | | `sessions.venue_id` / `venue_name` |
| 7 | 集合場所 | | `sessions.meeting_point`。屋外のときだけ欄を出す |
| 8 | 撮影日 | `*` | `sessions.session_date` |
| 9 | 集合時刻 | | `slots.meeting_at`（撮影日と合成）。開始時刻の左に出す |
| 10 | 開始時刻 | `*` | `slots.start_at`（撮影日と合成） |
| 11 | 終了時刻 | `*` | `slots.planned_minutes`（開始との差分を分で） |
| 12 | 撮影料（円） | | `slots.booking_fee`。空欄は0円。0以上の整数 |
| 13 | 支払方法 | | `slots.fee_payment_timing`（当日 / 事前 / 支払済み）。撮影料の隣に出す。既定は未選択 |
| 14 | 支払日 | | `slots.fee_payment_date`。事前のときだけ欄を出す |
| 15 | 衣装系オプション | | `slots.costume_options` |
| 16 | 撮影方法オプション | | `slots.shooting_method_options` |
| 17 | メモ | | `sessions.memo`。予約から選ぶと引き継ぐ。確定撮影情報のカードと撮影情報の詳細に表示し、撮影情報の編集で変更できる |


- **セッション・大撮は `slot_models` を持たない。** 予約から確定するときにこれらの区分へ変えたら、
  予約時のモデルの紐づけを外す（モデルマスタの行は残す）
- スタジオを選ぶと、入力済みの集合場所は保存しない
- 事前以外を選ぶと、入力済みの支払日は保存しない
- 終了時刻が開始時刻以前ならエラーにして保存しない
- 予約から確定する場合、予約時に仮置きした `slots.start_at`（撮影日の 0 時）を実時刻に直す。
  予約の初期値も 0:00 のときは「未入力」として扱い、時刻欄を空で出す
- 同じモデルが既に枠に紐づいていれば追加しない（`unique(slot_id, model_id)` 違反を避ける）
- 保存先ストレージURL はこの画面では扱わない。撮影後に「確定撮影情報」から登録する

### 8.10 確定撮影情報

「確定撮影情報入力」で登録した内容を一覧し、**撮影料とオプションを編集し、撮影後に保存先ストレージURLを登録する画面**。
対象は `sessions.status = 'confirmed'`、1枠 = 1カード、撮影日の新しい順。

表示: 撮影会名 / 撮影コンセプト / 撮影日と開始〜終了時刻 / 集合時刻・支払方法と支払日（入力があるときだけ） / 場所区分 / 場所 / 集合場所（入力があるときだけ） /
モデル名とモデルアカウント / 編集ボタン

| バッジ | 条件 |
|---|---|
| 撮影前 | 撮影の開始時刻がまだ先 |
| 撮影中 | 開始時刻を過ぎていて、撮影が終わっていない |
| データ未登録 | 撮影が終わっていて保存先が空 |
| データ登録済み | `storage_urls` か `storage_path` が入っている |

- **「編集」で確定した内容をすべて修正できる。** 撮影日を過ぎていない撮影も対象（確定後にオプションが増えることがあるため）。
  画面は撮影情報検索の編集画面（`/archives/search/edit?source=slot&id=…&from=info`、8.11.1）を使い、
  `from=info` のときは保存後に確定撮影情報へ戻る（履歴は置き換える）。キャンセルは1つ前の画面へ戻る
- 撮影料（`booking_fee`）と衣装系・撮影方法オプションはその場でも編集できる。変更が無いあいだ保存ボタンは無効
- 撮影料は枠の料金なのでモデル別の集計（`v_model_stats`）には入らない。`v_session_costs` と料金リマインドには入る
- 保存先はその場で編集して登録する。「追加」で最大10個まで増やせる。空欄は保存しない。変更が無いあいだ保存ボタンは無効
- **保存先は撮影が終わるまで操作できない。** 終了は `start_at + planned_minutes + extended_minutes`（`lib/slot-time.ts`）。
  `shoot_status = 'shot'` の枠は終了時刻より前でも操作できる。保存処理でも同じ条件で拒否する。
  撮影情報検索の編集画面も同じ。開いたままでも1分以内に操作できるようになる
- 判定は端末の時計で行う。サーバ側（DB の制約）では止めていない
- **1つでも登録すると撮影リマインドから外れる**（判定は `storage_path` または `storage_urls`）
- 撮影済みで未登録の件数を画面上部に出す
- モデルのアカウント欄は URL ならリンク、`@ハンドル` だけならテキストで出す

### 8.11.1 撮影情報検索

上に検索条件、下に結果を出す。**「検索」を押したとき（Enter でも可）の条件で結果を出し、**入力の途中では結果を変えない。
検索前は結果を出さない。条件が空のまま検索すると全件を出す。「いつから」が「いつまで」より後なら検索しない。
「条件をクリア」は入力と結果の両方を消す。
検索した条件は URL のクエリに持つので、詳細から戻っても結果が残る。読み取りは `lib/queries/archives.ts`。

| 条件 | 一致の仕方 |
|---|---|
| 撮影会名 | 部分一致。大文字小文字と前後の空白を無視 |
| モデル名 | 同上。複数モデルならいずれかに一致 |
| 撮影日（いつから / いつまで） | 両端を含む範囲。片方だけでもよい |
| 撮影場所 | 部分一致。マスタに紐づく場所はマスタの現在の名前で見る |

結果: 撮影日 / モデル / 撮影会名 / ストレージのURL / 詳細ボタン / 編集ボタン。撮影日の新しい順。
**撮影会名を空にして登録した撮影は、撮影会名を「—」で出す**（`eventNameOf`）。`title` にはコンセプトか
「葵 撮影」のような自動の名前が入っているので、撮影会マスタに紐づかず、`title` がコンセプトか
`fallbackShootTitle` と同じなら空だったとみなす（撮影会の自動登録より前の行も、自動の名前でなければ撮影会名として出す）。
http(s) の URL だけリンクにする（入力欄の型は `javascript:` なども通すため）。

**対象は `v_shoot_history_all` より広い。** 遡及登録に加えて、運用フローの枠は `shoot_status = 'shot'` と、
**確定済み（`confirmed` / `done`）で撮影日時を過ぎた枠**を含める。撮影済みへ変更する画面がまだ無いので、
ビューに合わせると確定撮影情報入力で登録した撮影が検索に出ないため。中止・不参加と論理削除は出さない。
ダッシュボードの「直近の撮影済みデータ」はビューどおり `shot` だけを見ているので、対象が異なる。

**詳細** `/archives/search/detail?source=&id=` は登録内容を読み取り専用で表示する。
**編集** `/archives/search/edit?source=&id=` は登録時と同じ項目を変更する。

- 動的ルートにしないのは、事前レンダリングされずオフラインで開けなくなるため
- 運用フローは `sessions` / `slots` を更新し、`status` は変えない。遡及登録は `shoot_history` を更新する。
  未来の撮影日はエラー（遡及登録のみ）
- モデルを変えると紐づけの `model_id` を更新する。作り直すとモデル料や納品の記録が消えるため。
  モデルなしの区分に変えると紐づけを外す
- 複数モデルの撮影は先頭のモデルをフォームに出し、新しい名前を入力すると追加する（既存の紐づけは外さない）
- 撮影日を過ぎていない確定済みの撮影は検索に出ないので、検索からは編集できない（確定撮影情報の「編集」から開く。8.10）

### 8.11.2 過去撮影情報

撮影実績と撮影予定をモデル別と撮影会別に集計する。どちらも最新の日付の新しい順で、
撮影予定しか無いもの（日付が無いもの）は最後に名前の順で並べる。読み取りは `lib/queries/stats.ts`。

| 表 | 項目 | 定義 |
|---|---|---|
| モデル別情報 | モデル名 | マスタから論理削除したモデルも実績として出す |
| | 撮影回数 | 撮影イベントの数。同じ session の枠は1回と数える |
| | 撮影予定回数 | 撮影予定の撮影イベントの数。数え方は撮影回数と同じ |
| | 初撮影日 / 最新撮影日 | そのモデルの撮影日の最小 / 最大。撮影予定は含めない（撮影予定しか無ければ「—」） |
| 撮影会別情報 | 撮影会名 | `organizers.name` |
| | 撮影モデル数 | モデルの人数。同じモデルは1人と数える |
| | 撮影予定モデル数 | 撮影予定のモデルの人数。同じモデルは1人と数える |
| | 初利用日 / 最新利用日 | その撮影会の撮影日の最小 / 最大。撮影予定は含めない（撮影予定しか無ければ「—」） |

- **対象は撮影情報検索と同じ**（`loadShootArchive`、8.11.1）。確定済みで撮影日時を過ぎた枠も含むので、
  `shoot_status = 'shot'` だけを見る `v_model_stats` より広い
- 撮影会別は `organizer_id` のある撮影だけを数える。撮影会名が未入力の撮影のタイトルは自動のもの（「葵 撮影」など）で、
  撮影会として扱えないため。撮影会の自動登録（8.12.1）より前に登録した撮影も含まれない
- **撮影予定は、確定済みでまだ撮影日時になっていない枠**（`loadUpcomingShoots`）。撮影情報検索の対象のちょうど裏返しで、
  確定済みの枠はどちらか一方にだけ数える。予約段階（`sessions.status` が確定前）と、中止・不参加の枠は含めない
- 撮影実績も撮影予定も無いモデル・撮影会は出さない
- 撮影希望は撮影の実績ではないので数えない

### 8.12 モデルマスタ

一覧: モデル名（`models.name`） / 所属（メインの `models.affiliation`。未入力は「—」。その他の所属があれば「ほかN」） / 詳細ボタン / 編集ボタン

- 論理削除したモデルは出さない
- 読み（`name_kana`）の順。読みが無ければ名前で並べる
- 新規登録と削除の画面はまだない。モデルは各画面の入力で自動で登録される

**詳細** `/masters/models/detail?id=` は各カラムの値と別名義（読み付き）、モデルアカウントを全部表示する。

**編集** `/masters/models/edit?id=` で変更できるのは次の項目。

`name` / `name_kana` / 別名義（`model_former_names`） / 所属（`affiliation` + `sub_affiliations`） /
`sns_accounts` / `contact_method` / `contact_value` / `is_favorite` / `status` / `notes`

- **`avatar_url` / `tags` / `rating` は使わないので詳細にも編集にも出さない**（カラムと値は残す）
- **`id` は変更不可。** `user_id` / `created_at` / `updated_at` / `deleted_at` も編集画面に出さない
  （`user_id` は所有者、日時はトリガと論理削除が管理するため）
- **所属は「所属を追加」で増やし、1つをメインに選ぶ。** メインは `affiliation`、それ以外は `sub_affiliations` に入る。
  空欄と重複（大文字小文字の違いを含む）は除く。メインに選んだ欄が空なら、残った所属の先頭をメインにする
- `name` は空にできず、同じ名前で所属（メイン・その他のどれか）が重なるモデルがあればエラーにする。
  予約などの入力でどちらのモデルか決められなくなるため。所属なしどうしの同名もエラー（サーバの一意制約と同じ）
- **所属のうち撮影会マスタに無いものは、保存時に撮影会として登録する**（`organizers`）。
  「フリー」は登録しない。照合は大文字小文字を区別せず、論理削除した撮影会は無いものとして扱う。
  登録したら「撮影会マスタに「…」を登録しました」と表示する
- **別名義は「別名義を追加」で登録する。** 改名前の名前や別の活動名。各行に読み（`name_kana`、任意）を持つ。
  名義が空欄の行と重複は除く。消した別名義は物理削除する（tombstone で同期）。
  残したものは作り直さず、読みが変わったときだけ更新する
- **モデルアカウントは「アカウントを追加」で増やす。** 各行で種類（X / Instagram / その他）を選び、URL か @ハンドルを入れる。
  同じ種類を複数登録できる。空欄と重複（同じ種類で同じ値。大文字小文字は区別しない）は除く。
  全部消すと `sns_accounts` は `[]` になり、古い `sns_links` も表示しない
- 移行前の `sns_links` は、マイグレーションで `sns_accounts` に移す（X → Instagram → その他の順）。
  移行前に端末で作ったローカル行は `sns_accounts` を持たないので、読むときに `sns_links` から作る（`lib/model-accounts.ts`）
- `status` は活動中 / 休止・引退。**`ng`（今後撮影しない）は選択肢から外した。** enum の値は残っているので、
  `ng` の行は詳細・編集では休止・引退として表示し、保存すると `inactive` で書き戻す（`lib/model-status.ts`）。
  入力候補からも除外しない
- 予約などから自動で作った行はローカルでカラムが欠けていることがあるので、読むときに既定値で補う

### 8.12.2 モデルの自動登録（モデル名 × 撮影会名）

予約情報入力・確定撮影情報入力・過去撮影登録では、**モデル名と撮影会名の組み合わせでモデルを見分ける。**
組み合わせが新しければ、撮影会名を所属（`affiliation`）にしたモデルをモデルマスタに登録する。

| 入力 | 使うモデル | 無いときに登録する所属 |
|---|---|---|
| 撮影会名あり | 同じ名前で、所属（メイン・その他のどれか）が撮影会名と同じ（大文字小文字の違いを含む）モデル | 撮影会名 |
| 撮影会名が空 | 同じ名前で、所属が「フリー」か未設定のモデル | 「フリー」 |

- 新しく登録したら、保存後に「新規モデルが登録されました。モデルマスタを編集しますか？」と確認する。
  「はい」ならそのモデルの編集画面へ、「いいえ」なら通常の遷移先へ進む（`lib/new-model-prompt.ts`）
- **予約の選択と撮影情報の編集では、撮影会名を変えていなければ今のモデルを保つ。** フォームには既存のタイトル
  （撮影会名が未入力なら「葵 撮影」のような自動のもの）が入るので、そのまま照合すると別のモデルが作られるため。
  モデル名も変えていなければ、所属を手で変えたモデルもそのまま使う。撮影会名が未入力の撮影は、撮影会名が空として照合する
- モデルを変えると紐づけを付け替える（元のモデルは外す。モデル料などの記録は残す）
- 撮影希望モデル登録は名前だけで照合する（所属が「フリー」、未設定、その他の順）。新しく作るときの所属は「フリー」
- モデル名の入力候補は名前で重複を除く

### 8.12.1 撮影会マスタ

一覧: 撮影会名（`organizers.name`） / 拠点（`organizers.base_location`。未入力は「—」） / 詳細ボタン / 編集ボタン

新規登録と削除の画面はまだない。撮影会は各画面の入力で自動で登録される（下記）。

**詳細** `/masters/organizers/detail?id=` は全カラムの値を表示する。URL は http(s) のときだけリンクにする。
アカウントはモデルと同じく、URL ならリンク、`@ハンドル` だけならテキストで出す。

**編集** `/masters/organizers/edit?id=` で変更できるのは
`name` / `name_kana` / `base_location` / `url` / `sns_accounts` / `contact` / `notes` / `is_favorite`。

- **アカウントは「アカウントを追加」で増やす。** 入力欄はモデルマスタと共通（`components/forms/AccountsField.tsx`）。
  種類（X / Instagram / その他）を選んで URL か @ハンドルを入れる。空欄と重複（同じ種類で同じ値。大文字小文字は区別しない）は除く

- **`id` は変更不可。** `user_id` / `created_at` / `updated_at` / `deleted_at` も編集画面に出さない
- `name` は空にできず、他の撮影会と同じ名前（大文字小文字の違いを含む）にできない（サーバの一意制約と同じ条件）
- **名前を変えると、古い名前を所属に持つモデルの所属も新しい名前に書き換える。**
  メイン（`affiliation`）とその他（`sub_affiliations`）の両方が対象で、大文字小文字の違いも同じ名前として扱う。
  大文字小文字だけの変更でも表記をそろえる。論理削除したモデルは書き換えない（`lib/actions/organizers.ts`）
  - 書き換えで同じモデルの所属が重なったら1つにまとめる（メインを残す）
  - 書き換えると、同じ名前で所属が重なるモデルが2つできる場合は、エラーにして撮影会もモデルも変更しない。
    予約などの入力でどちらのモデルか決められなくなり、メインの所属どうしならサーバの一意制約でも同期が失敗するため
- 登録済みの撮影のタイトル（`sessions.title` / `shoot_history.title`）は書き換えない。入力した時点の名前を持つ

- 論理削除した撮影会は出さない。読み（`name_kana`）の順で、読みが無ければ名前で並べる
- **各画面で入力した撮影会名を、モデル名と同じくマスタへ自動で登録する。** 同名（大文字小文字の違いを含む）は増やさない。
  予約・確定・過去撮影は `organizer_id` で紐づける。撮影希望は日付も枠も無いので、登録だけ行う
- 撮影会名が空なら登録しない。タイトルをコンセプトやモデル名から作っても、マスタには入れない
- 予約の選択や編集ではフォームに既存のタイトルが入るので、**名前を変えていないときは登録せず、今の紐づけを保つ**。
  自動のタイトル（「葵 撮影」など）がマスタに入るのを防ぐため
- この仕組みの導入前に登録した撮影の撮影会名は、自動のタイトルと区別できないので取り込まない

### 8.12.3 ロケ地・スタジオマスタ

一覧: 撮影場所（`venues.name`） / 詳細ボタン / 編集ボタン。論理削除した場所は出さない。名前の順（読みのカラムは無い）。
新規登録と削除の画面はまだない。

- **確定撮影情報入力・過去撮影登録（とその編集）で入力した場所を、マスタへ自動で登録する**（`resolveVenue`）。
  同名（大文字小文字の違いを含む）は増やさず、`venue_id` で紐づける。`venue_name` には入力した名前も残す。
  種別（`kind`）は場所区分から決める（屋外 → `location`、スタジオ → `studio`）
- **予約情報入力では登録しない。** 予約段階で場所マスタが増え続けるのを避けるため（同名があれば紐づけだけ行う）。
  予約から確定すると、その時点で登録する
- 場所が空なら登録しない。論理削除した場所は無いものとして扱い、同じ名前なら新しく登録する
- この仕組みの導入前に登録した撮影の場所は取り込まない（その撮影を編集して保存すると登録される）

**詳細** `/masters/venues/detail?id=` は全カラムの値を表示する。URL は http(s) のときだけリンクにする。

**編集** `/masters/venues/edit?id=` で変更できるのは
`name` / `kind` / `address` / `nearest_station` / `url` / `hourly_rate` / `notes` / `is_favorite`。

- **`id` は変更不可。** `user_id` / `created_at` / `updated_at` / `deleted_at` も編集画面に出さない
- `name` は空にできず、他の場所と同じ名前（大文字小文字の違いを含む）にできない（サーバの一意制約と同じ条件）
- `hourly_rate` は0以上の整数。カンマ区切りも受け付ける。空欄は NULL
- **名前を変えると、紐づく撮影の場所の表示も新しい名前になる**（撮影の表示は `venue_id` があればマスタの名前を使うため）
